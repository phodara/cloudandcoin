# LD2410C Presence Sleep Plan

> Generated by ChatGPT

These notes are for adding a Hi-Link `HLK-LD2410C` mmWave human presence
sensor to the Hosyond / LCDWIKI / Elecrow-style `3.5" LCD Display ESP32-32E
320x480 Resistance Touch` board used by this project.

## Goal

Use the LD2410C as a low-power presence sentry so the dashboard can turn off the
display and place the ESP32 into a sleep-oriented idle state when nobody is
nearby.

Desired behavior:

```text
Dashboard active
        |
No touch / no presence for configured timeout
        |
Backlight off, network refreshes paused
        |
ESP32 light sleep or low-activity idle
        |
Wake every few seconds by timer
        |
Check LD2410C presence / distance
        |
Presence within configured distance -> wake dashboard
No presence or too far away       -> sleep again
```

## Sensor Interface

The LD2410C provides two useful interfaces:

- `OUT`: simple digital target status output.
- `UART`: richer presence, movement, static target, and distance data.

For the first implementation, use `OUT` for a simple presence signal. Add UART
only when firmware-controlled distance filtering or sensor configuration is
needed.

The module is normally powered from `5V`. Its GPIO/UART logic level is `3.3V`,
so the `OUT` and UART pins can connect to ESP32 GPIO inputs directly.

## Board Connector Availability

Visible connectors on this board include:

- `IO35 / IO39`
- `SPI`: `IO23`, `IO19`, `IO18`, `IO21`, `GND`, `5V`
- `I2C`: `3.3V`, `IO32`, `IO25`, `GND`
- `UART`: `TXD`, `RXD`, `GND`, `5V`
- `BAT`

Current firmware already uses:

- Display/touch SPI: `IO12`, `IO13`, `IO14`
- Display control: `IO15`, `IO2`, `IO27`
- Touch chip select: `IO33`
- SD card on separate `HSPI`: `IO5`, `IO18`, `IO19`, `IO23`
- Battery ADC: `IO34`

Avoid `IO18`, `IO19`, and `IO23` for this sensor because the SD card uses them.
Avoid `TXD` / `RXD` for the sensor UART if possible because those are the
primary USB programming and serial monitor pins, usually `IO1` and `IO3`.

## Recommended Wiring

Minimal wiring:

```text
LD2410C VCC -> board UART 5V
LD2410C GND -> board UART GND
LD2410C OUT -> board IO39
```

`IO39` is recommended for `OUT` because it is input-only, exposed on the board,
and currently unused by this firmware.

Optional UART wiring:

```text
LD2410C TX -> board IO32  // ESP32 UART RX
LD2410C RX -> board IO25  // ESP32 UART TX
```

`IO32` and `IO25` are exposed on the board's I2C connector and can be used as
ordinary GPIO/UART pins if no I2C peripheral is attached. The board manual notes
I2C pull-up resistors on these lines. If UART communication is flaky, inspect or
remove those pull-ups before assuming the sensor or firmware is bad.

## IO35 Caveat

`IO35` is also a good input-only candidate for LD2410C `OUT`, but
`docs/CC_charging_monitor_wiring_notes.md` reserves it as the preferred future
battery charging-status input.

Use only one of these plans on `IO35`:

- LD2410C `OUT`
- TP4054 `CHRG` charging monitor

If both features are desired, use `IO39` for LD2410C `OUT` and keep `IO35` for
the charging monitor.

## Power Notes

The LD2410C should be powered from a board `5V` connector, not from an ESP32
GPIO pin. Keep sensor ground tied to board ground.

Do not connect board `5V` directly to any ESP32 GPIO. Only connect LD2410C
logic outputs, which are expected to be `3.3V`, to ESP32 GPIO.

The LD2410C remains powered while the ESP32/display sleep. This is intentional:
the sensor acts as the always-on presence detector. This means the design saves
display/Wi-Fi/ESP32 activity power, but it is not a true zero-current sleep
state.

## Firmware Plan

Prefer `ESP32 light sleep` for the initial implementation. Deep sleep would
reboot the firmware on every wake, which is disruptive for LVGL state, SD card
state, Wi-Fi, the web server, and the FreeRTOS data worker.

Suggested new file:

```text
src/app/presence_sensor.inc
```

Suggested compile-time defaults:

```cpp
#define ENABLE_PRESENCE_SLEEP       1
#define PRESENCE_OUT_PIN            39
#define PRESENCE_UART_RX_PIN        32
#define PRESENCE_UART_TX_PIN        25
#define PRESENCE_USE_UART           0
#define PRESENCE_SLEEP_AFTER_SEC    60
#define PRESENCE_POLL_SEC           5
#define PRESENCE_MAX_DISTANCE_CM    250
```

Suggested SD `/secrets.txt` runtime keys:

```text
presence_enabled=1
presence_sleep_after_seconds=60
presence_poll_seconds=5
presence_max_distance_cm=250
presence_use_uart=0
```

Pin choices should stay compile-time unless there is a strong reason to make
them runtime-configurable. Runtime pin configuration makes it easier to choose a
bad boot or peripheral pin from the web UI.

## Runtime State Machine

Add a small display/power state machine near the existing UI runtime scheduling:

```text
ACTIVE
DIMMED
SLEEPING
WAKING
```

Suggested behavior:

- `ACTIVE`: normal dashboard, touch, web, weather, and crypto refresh behavior.
- `DIMMED`: optional transition state after idle timeout, reduced brightness.
- `SLEEPING`: backlight off, data refreshes skipped, timer wake enabled.
- `WAKING`: restore backlight, redraw current page, resume refresh scheduling.

Touch input should reset the idle timer while active. Presence should also reset
the idle timer once the sensor is proven reliable.

## Distance Filtering Options

The `OUT` pin is a **boolean signal only** — `HIGH` when the sensor detects
presence, `LOW` when it does not. It carries no distance or range information.

The `UART` interface provides richer data: actual detected distance in
centimetres, separate moving-target vs. stationary-target readings, and
signal energy levels.

There are two ways to enforce "wake only if presence is within a given
distance":

1. Configure the LD2410C detection gates externally and use only `OUT`.
2. Read LD2410C UART data and let firmware compare the detected distance to
   `presence_max_distance_cm`.

Option 1 is simpler and should be the first milestone.

**Tuning detection range without UART firmware work:** The LD2410C has
configurable detection gates built into the sensor itself. These can be
adjusted using the Hi-Link Bluetooth configuration app (available for iOS and
Android) or by sending UART config commands directly to the sensor from a PC.
Once the gates are set, the sensor enforces the range limit autonomously and
`OUT` continues to behave as a simple boolean — no ESP32 code changes needed.
This makes Phase 5 optional: if the Bluetooth app provides sufficient range
control for the installation, UART parsing in firmware may never be necessary.

Option 2 is more flexible and keeps the distance rule visible in firmware/config, but it
requires UART parsing and more testing around sleep/wake timing.

## Implementation Phases

1. Wire `VCC`, `GND`, and `OUT`; prove the firmware can read presence while the
   dashboard stays fully awake.
2. Add a debug/status line to Serial or `/info` showing presence state.
3. Add backlight auto-off and wake without ESP32 light sleep.
4. Add timer-based ESP32 light sleep and wake polling.
5. Add UART distance parsing if software-controlled distance filtering is still
   desired.
6. Tune sleep timeout, polling interval, and false-positive behavior in the
   actual enclosure and mounting location.

## Test Checklist

After implementation, test:

- Normal page navigation still works after SD initialization.
- Weather, Crypto, Pair Trading, and Signals pages still refresh after wake.
- Web routes still respond after repeated sleep/wake cycles.
- Touch wakes or resets idle timing as expected.
- Backlight restores to the configured brightness from `/secrets.txt`.
- SD card remains stable after multiple sleep/wake cycles.
- Presence does not trigger from movement outside the desired distance.
- No upload or serial monitor instability is introduced by the chosen pins.
